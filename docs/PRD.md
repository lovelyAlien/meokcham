# PRD: 금지 음식 일일 체크 서비스 "먹참"

- 작성일: 2026-10-20
- 상태: 초안
- 범위: MVP

> **요약**
> - "몸에 안 좋은 음식을 먹지 말아야지"라는 다짐이 매일 깨지는 문제를 푼다.
> - 사용자가 스스로 금지 음식을 정하고, 하루 한 번 "오늘 먹었나?"에 답하면, 그 결과가 GitHub 잔디처럼 쌓인다.
> - 칼로리·영양 계산이 아니라 **다짐을 지켰는지**만 기록한다. 기록 비용은 하루 10초 이내.

## 1. 목표

### 1.1 문제

- "오늘부터 라면·과자·탄산 끊는다"는 다짐은 쉽게 하지만, **며칠 지나면 다짐 자체를 잊는다.**
- 기존 식단 앱은 끼니마다 음식과 칼로리를 입력해야 해서 기록 비용이 크다. "금지 음식을 먹었냐, 안 먹었냐"라는 단순한 질문에 답하기엔 과하다.
- 기록을 하더라도 **얼마나 잘 지키고 있는지 한눈에 보이지 않아** 동기 부여가 약하다.

### 1.2 제품 목적

사용자가 **스스로 정한 금지 음식을 매일 의식하고, 지킨 날이 쌓이는 것을 눈으로 보며, 다짐을 오래 유지**하게 한다.

### 1.3 사용자에게 미치는 영향

| 지금 | 먹참 이후 |
| --- | --- |
| 다짐을 했는지조차 며칠 뒤엔 잊음 | 매일 정해진 시각 알림이 다짐을 상기시킴 |
| "요즘 좀 덜 먹는 것 같은데?" 같은 막연한 느낌 | 지난 1년이 초록/빨강 칸으로 한눈에 보임 |
| 한 번 어기면 "망했다" 하고 포기 | 빨간 칸 하나 뒤에 다시 초록이 이어지는 걸 보며 복귀 |

### 1.4 제품(프로젝트) 차원의 목표

- **개인 문제 해결:** 만든 사람이 직접 매일 쓰는 서비스(도그푸딩)가 된다.
- **포트폴리오:** 작은 도메인이지만 일 단위 집계, 타임존 처리, 알림 스케줄링, 시각화용 조회 API 같은 백엔드 설계 포인트를 명확히 보여준다.
- **확장 가능성:** 실사용자가 생기면 공개 서비스로 운영할 수 있는 구조를 갖춘다.

### 1.5 성공 지표 (제안)

| 지표 | 정의 | MVP 목표(제안) |
| --- | --- | --- |
| 일일 기록률 | 기록한 날 / 가입 후 경과일 | 70% 이상 |
| 30일 리텐션 | 가입 30일 후에도 주 3회 이상 기록하는 사용자 비율 | 40% 이상 |
| 기록 소요 시간 | 알림 수신 → 기록 완료 | 중앙값 10초 이내 |
| 준수일 비율 추이 | 월별 "안 먹은 날" 비율 | 첫 달 대비 셋째 달 상승 |

> 첫 단계에서는 만든 사람 본인이 **30일 연속 기록**하는 것을 1차 성공 기준으로 삼는다.

## 2. 대상 고객

### 2.1 주 페르소나: "다짐은 매일, 실천은 가끔" 직장인

- 20~30대 직장인 / 개발자. 야근·회식·배달 앱으로 군것질과 야식이 잦다.
- 다이어트 앱처럼 무겁게 관리하고 싶지는 않다. **딱 몇 가지만 끊고 싶다.** (예: 야식 라면, 탄산음료, 과자)
- GitHub 잔디에 익숙하고, 잔디를 채우는 것 자체에서 동기를 얻는다.
- 원하는 것: "오늘 지켰는지 빠르게 체크하고, 내가 얼마나 잘하고 있는지 한눈에 보고 싶다."

### 2.2 보조 세그먼트

- **특정 음식을 줄이고 싶은 사람:** 카페인·술·밀가루·설탕 등 한두 가지 품목만 의식적으로 줄이려는 사람.
- **습관 트래커 사용자:** 이미 습관 앱을 쓰지만 "하지 않기(금지)" 습관을 다루는 데는 불편함을 느끼는 사람.

### 2.3 MVP에서 대상이 아닌 사용자

- 칼로리·영양소를 정밀하게 관리하려는 사람 (기존 식단 앱이 더 적합)
- 의료적 식이 제한(알레르기, 질환 관리)이 목적인 사람. 먹참은 건강 조언이나 의료적 판단을 하지 않는다.

## 3. 전략적 적합성

먹참은 회사 제품이 아니라 개인 사이드 프로젝트이므로, "전략"은 **사이드 프로젝트를 고르는 기준**에 비춰 정리한다.

### 3.1 "포트폴리오이면서 진짜로 쓰는 제품"이라는 기준에 맞는다

- 만든 사람이 직접 겪는 문제라 요구사항을 스스로 검증할 수 있고, 매일 쓰면서 개선점을 바로 찾을 수 있다.
- 도메인은 단순하지만 설계 고민이 진짜로 존재한다.

| 설계 포인트 | 왜 흥미로운가 |
| --- | --- |
| **"하루"의 정의** | 자정을 넘긴 야식은 어느 날 기록인가? 사용자 타임존과 하루 경계(예: 새벽 4시)를 어떻게 다룰 것인가 |
| **잔디 조회** | 1년치(365칸) 데이터를 한 번에 내려주는 조회 API, 집계·캐싱 전략 |
| **알림 스케줄링** | 사용자마다 다른 알림 시각·타임존에 맞춘 배치/스케줄러 설계 |
| **기록 정정** | 지난 날 기록 수정 허용 범위, 이력 관리 |
| **연속 기록(스트릭)** | 현재/최장 연속 준수일 계산과 갱신 |

### 3.2 작게 시작해서 끝까지 낼 수 있다

- 핵심 루프(금지 음식 설정 → 매일 체크 → 잔디 확인)가 짧아서 MVP를 빠르게 출시하고, 실제 사용 데이터로 다음 기능을 정할 수 있다.

### 3.3 확장 경로가 열려 있다

- 금지 음식 외에 "하지 않기" 습관 전반(SNS 사용, 늦은 취침 등)으로 일반화할 여지가 있다. 단, MVP에서는 **음식에만 집중**해 메시지를 선명하게 유지한다.

## 4. 우리의 신념

### 신념 1. 기록이 쉬울수록 오래 간다

> 기록 비용이 하루 10초 이내면, 사용자는 매일 기록한다.

- 끼니별 입력, 사진, 칼로리 같은 부담을 모두 덜어내고 **"오늘 먹었다 / 안 먹었다"** 한 번의 탭으로 끝낸다.
- 검증 방법: 일일 기록률, 기록 소요 시간.

### 신념 2. 눈에 보이는 연속성이 동기가 된다

> 잔디처럼 지킨 날이 쌓이는 것을 보면, 그 흐름을 끊고 싶지 않아진다.

- GitHub 잔디는 "칸 하나를 비우기 싫어서" 커밋하게 만드는 검증된 시각 장치다. 같은 심리를 식습관에 적용한다.
- 검증 방법: 잔디 화면 조회 빈도와 다음 날 기록률의 상관관계.

### 신념 3. 하루 한 번의 상기가 다짐을 살린다

> 다짐이 깨지는 가장 큰 이유는 의지 부족이 아니라 **망각**이다.

- 매일 같은 시각의 알림이 "나 이거 안 먹기로 했지"를 다시 떠올리게 한다.
- 검증 방법: 알림 켠 사용자와 끈 사용자의 기록률·준수일 비율 비교.

### 신념 4. 실패를 벌하지 않아야 다시 돌아온다

> 빨간 칸 하나가 "다 망했다"로 이어지면 사용자는 떠난다.

- 어긴 날도 정직하게 기록하는 것 자체를 가치 있게 여긴다. 기록한 날은 "미기록(빈 칸)"과 분명히 구분한다.
- 스트릭이 끊겨도 **누적 준수일, 이번 달 준수율** 같은 끊기지 않는 지표를 함께 보여준다.
- 검증 방법: 빨간 칸 기록 다음 날의 재기록률.

### 신념 5. 스스로 정한 규칙이어야 지킨다

> 남이 정해준 "건강에 나쁜 음식 목록"보다 내가 고른 목록이 더 오래 간다.

- 서비스는 무엇이 몸에 나쁜지 판단하지 않는다. 금지 목록은 전적으로 사용자가 정한다. (빠른 설정을 위한 예시 목록은 제공 가능)

## 5. 솔루션 제약 조건 및 원칙

### 5.1 제품 원칙

1. **10초 원칙:** 알림을 받고 기록을 마치기까지 10초를 넘기지 않는다. 기록 단위는 "그날 전체에 대해 먹음/안 먹음" 하나다. "안 먹었다"는 한 번의 탭으로 끝나고, "먹었다"일 때만 먹은 음식을 고른다(필수, 다중 선택). 지킨 날은 모든 금지 음식을 지킨 것이므로, 이 방식만으로 음식별 데이터가 빠짐없이 모인다.
2. **한눈에 원칙:** 첫 화면에서 최근 1년의 잔디와 오늘 기록 상태가 바로 보인다.
3. **정직한 기록 원칙:** 세 가지 상태를 명확히 구분한다.

   | 상태 | 의미 | 표시 |
   | --- | --- | --- |
   | 지킴 | 금지 음식을 하나도 먹지 않음 | 초록 |
   | 어김 | 금지 음식을 하나 이상 먹음 | 빨강 |
   | 미기록 | 그날 기록하지 않음 | 회색(빈 칸) |

4. **비난하지 않는 톤:** 어긴 날에도 문구는 중립적이거나 격려하는 방향으로 쓴다. 경고·처벌성 연출(진동 경고, 실패 강조 애니메이션 등)은 하지 않는다.
5. **사용자가 규칙의 주인:** 금지 음식의 추가·삭제·이름 변경은 언제든 가능하다. 서비스가 특정 음식을 "나쁘다"고 단정하지 않는다.

### 5.2 디자인 제약

- **GitHub Contribution Graph를 차용한다.** 7행(요일) × 약 53열(주) 격자, 가로 스크롤 없이 1년이 보이는 밀도를 기본으로 한다.
- MVP는 초록/빨강/회색 **단색 3색**만 쓰고 색 농도는 쓰지 않는다. (이후 후보: 지킨 날의 초록 농도를 "최근 7일 중 지킨 날 수"로 표현. 빨강 하나로 0이 되지 않아 복귀가 보이는 방식이다. 빨강에는 농도를 쓰지 않는다.) 단, **색만으로 의미를 전달하지 않는다**(색각 이상 사용자 고려). 칸 탭 시 날짜·상태·먹은 음식을 텍스트로 보여준다.
- 모바일 화면 폭에서 1년치가 너무 작으면 최근 N개월로 접어 보여주는 방식을 고려한다.
- 다크 모드에서도 세 상태가 구분되어야 한다.

### 5.3 기술 제약

- **"하루"의 경계:** 사용자 타임존 기준으로 날짜를 계산한다. 서버는 UTC로 저장하되, 기록의 키는 `(사용자, 로컬 날짜)`로 둔다. 하루 경계는 **로컬 새벽 04:00 고정**이다(사용자 설정 불가). 즉 로컬 날짜 = `(현재 시각 - 4시간)`의 날짜이고, 새벽 1시 야식은 전날 칸에 들어간다.
- **하루 한 건:** 사용자·날짜당 기록은 하나다. 같은 날 다시 기록하면 덮어쓴다(최종 상태가 기준). 동시 요청에도 중복 기록이 생기지 않게 유니크 제약을 둔다.
- **지난 기록 수정:** 기록을 잊은 날을 소급 기록하거나 정정할 수 있어야 한다. 허용 기간(예: 최근 7일)은 정책으로 정한다.
- **금지 목록 변경과 과거 기록:** 목록 변경은 **즉시 적용되고, 기록 시점을 기준**으로 판단한다. 기록할 때 그 시점의 금지 목록 스냅샷과 먹은 음식을 함께 저장하므로, 금지 음식을 나중에 바꾸거나 지워도 이미 저장된 기록의 의미는 바뀌지 않는다. 같은 날 다시 기록하면 그때의 새 목록을 기준으로 덮어쓴다.
- **알림:** **서버 푸시(Expo Push)**로 보낸다. 서버 스케줄러가 사용자별 알림 시각·타임존을 보고, 그날 아직 기록하지 않은 사용자에게만 발송한다. 알림에는 액션 버튼("안 먹었다" 등)을 넣어 알림에서 바로 기록할 수 있게 한다.
- **조회 성능:** 잔디 1년치(최대 366건)는 단일 API 호출로 내려준다. 스트릭·준수율 같은 집계는 조회 시 계산하거나 기록 시 갱신하는 방식 중 하나를 택한다(미정).
- **플랫폼:** **크로스플랫폼 앱(Expo/React Native)**으로 시작한다. iOS 웹 푸시는 홈 화면에 추가한 PWA에서만 동작하고 알림 액션 버튼도 지원하지 않아서, 10초 원칙을 지킬 수 없기 때문이다. 도그푸딩은 iPhone 기준이다.
- **로그인:** **Apple + Google 소셜 로그인**을 쓴다. 비밀번호는 저장하지 않으며, 서드파티 로그인을 넣을 때 Apple 로그인도 함께 제공해야 한다는 App Store 규정을 충족한다. 백엔드는 ID 토큰을 검증한 뒤 자체 세션 또는 JWT를 발급한다.

### 5.4 비즈니스·운영 제약

- 1인(또는 2인) 사이드 프로젝트로 개발·운영한다. 운영 비용은 무료 티어 또는 최소 비용 범위 안에서 유지한다. 단, 다음 두 가지는 예외로 한다. Apple Developer Program(연 $99, 이미 사용 중, TestFlight 배포와 APNs 푸시에 필요), 네이버 클라우드 서버 1대(앱·DB를 함께 운영, [기술 스택](TECH_STACK.md) 참고).
- MVP에서는 수익화하지 않는다.
- **개인정보 최소 수집:** 식습관 기록은 민감하게 느껴질 수 있으므로 꼭 필요한 정보만 받는다. 기록은 기본적으로 비공개이며, 공유 기능은 MVP 범위 밖이다.
- **의료 서비스가 아님:** 먹참은 건강 조언, 진단, 식단 처방을 하지 않는다. 앱 내 문구도 이를 넘지 않는다.

### 5.5 하지 않는 것 (Non-goals)

- 칼로리·영양소 계산, 음식 사진 인식, 바코드 스캔
- 끼니 단위 상세 기록
- 친구·랭킹 등 소셜 기능 (MVP 이후 검토)
- 의료적 식이 관리

PRD 본문 범위 밖이지만, 다음 단계 논의를 위한 출발점으로 정리한다.

| ID | 기능 | 설명 | 우선순위 |
| --- | --- | --- | --- |
| F1 | 금지 음식 설정 | 금지 음식을 여러 개 등록·수정·삭제. 예시 목록에서 다중 선택으로 빠르게 시작 | Must |

| F3 | 잔디 보기 | 최근 1년을 초록/빨강/회색 단색 격자로 표시(농도 없음). 칸을 누르면 그날 상세 | Must |
| F4 | 일일 알림 | 사용자가 정한 시각에 서버 푸시로 "오늘 지켰나요?" 알림. 액션 버튼으로 알림에서 바로 기록 | Must |
| F5 | 스트릭·통계 | 현재/최장 연속 준수일, 이번 달 준수율 | Should |
| F6 | 지난 기록 정정 | 최근 N일 소급 기록·수정 | Should |
| F7 | 음식별 잔디 | 금지 음식 하나만 골라 그 음식의 잔디 보기 | Could |
