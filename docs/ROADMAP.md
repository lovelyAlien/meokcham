## 단계별 상세

### 0. 설계 마무리

이미 끝난 것: PRD, 기술 스택, DB 스키마(V1 마이그레이션 + 제약 조건 테스트), API 명세 초안.

- [x] **API 명세 확정:** [API_SPEC.md](API_SPEC.md) 결정 D1~D4 확정(음식 10개, 준수율 분모=기록한 날, 소급 제한 없음, 알림은 앱을 열어 기록). 남은 미결 사항은 해당 단계에서 정한다
- [ ] **UI/UX 설계:** 화면 목록과 흐름(온보딩 → 홈 → 기록 → 잔디 상세), 빈 상태, 잔디 3색 토큰(라이트·다크), 알림 문구
  - 현재 앱 화면은 모두 플레이스홀더이고 온보딩 라우트는 아직 없다.
  - 예시 금지 음식 목록(F1의 빠른 설정) 내용도 여기서 정한다.
- [ ] **엔티티 구현:** `User`, `SocialAccount`, `ForbiddenFood`, `DailyRecord`, `NotificationSetting`, `PushToken`, `RefreshToken` + enum 2개(`SocialProvider`, `RecordStatus`)
  - `forbidden_snapshot`, `eaten_foods`는 `jsonb` 매핑을 정한다(`@JdbcTypeCode(SqlTypes.JSON)` + record)
  - `daily_records` upsert는 JPA가 아니라 `JdbcClient`로 한다(`ON CONFLICT`)
  - `notification_settings`는 PK가 `user_id`라 `@MapsId` 매핑
  - `ddl-auto: validate`이므로 엔티티와 스키마가 어긋나면 기동 시점에 잡힌다
- [ ] **공통 예외 처리:** `@RestControllerAdvice`로 ProblemDetail + `code` 필드, 검증 실패 응답(`errors[]`). API 명세의 에러 형식을 모든 API가 따르게 하는 기반이라 첫 API보다 먼저 만든다.
- [ ] **테스트 방침:** 백엔드는 Testcontainers 통합 테스트 + 도메인 규칙 단위 테스트. 앱은 어디까지 자동 테스트할지 정한다(최소: typecheck, lint, 잔디 날짜 계산 같은 순수 함수 단위 테스트).
- [ ] `main` 푸시(현재 `origin/main`보다 2커밋 앞섬), CI 실행 확인

### 1. 인증

- 백엔드: ID 토큰 검증(Apple/Google), Access JWT 발급, Refresh rotation과 재사용 탐지, `SecurityConfig`에 JWT 검증 추가, **계정 삭제 API**(`DELETE /users/me`, App Store 필수 요건)
- 앱: 로그인 화면(`(auth)/login`), 토큰 저장(`expo-secure-store`), `apiFetch`에 Authorization 헤더와 401 재발급 처리
- **시크릿·환경 설정:** JWT 서명 키, Apple/Google 클라이언트 ID, Expo 토큰은 코드나 저장소에 넣지 않는다. 로컬은 환경 변수/`.env`(gitignore), 서버는 Compose 환경 변수로 주입한다.
- **EAS 개발 빌드:** Apple 로그인과 푸시는 Expo Go로 검증하기 어렵다. 번들 ID, 서명 인증서, 개발 빌드 설정을 이 단계에서 끝낸다(3단계 푸시가 같은 빌드를 쓴다).
- 의존: Apple Developer 계정, Google OAuth 클라이언트 설정

### 2. 핵심 루프

- 순서: 금지 음식 → 기록 → 잔디. 앞 단계가 뒤 단계의 입력이 된다.
- 백엔드: 04:00 경계 날짜 계산, 스냅샷 생성, 하루 한 건 upsert, 기록 있는 날만 내려주는 잔디 조회
- 앱: 온보딩(첫 금지 음식 설정), `foods` 화면, 오늘 기록(탭 1번), 잔디 격자(`react-native-svg`), 칸 탭 시 텍스트 상세
- **경계·타임존 테스트:** 03:59/04:00 직전후, 자정 넘긴 야식, 타임존 변경, 서머타임 지역(예: `America/Los_Angeles`)의 날짜 계산. 이 프로젝트의 핵심 설계 포인트라 반드시 테스트로 고정한다.
- 이 단계가 끝나면 알림 없이도 앱을 직접 열어 쓰며 도그푸딩을 시작할 수 있다.

### 3. 알림

- 가장 위험한 단계다. 실기기, APNs, Apple 계정이 필요하고 시뮬레이터에서는 검증할 수 없다.
- **기본 방식(확정):** 두 액션 버튼 모두 앱을 포그라운드로 열고 "안 먹었다"는 열리자마자 자동 기록한다([API 명세 D4](API_SPEC.md)). iOS에서 앱을 열지 않는 액션은 종료 상태에서 JS까지 전달되지 않을 수 있기 때문이다.
- **실험:** 구현 초기에 실기기(종료·백그라운드·포그라운드)로 앱을 열지 않는 액션이 되는지 확인한다. 안정적이면 "안 먹었다"만 백그라운드 처리로 바꾼다.
- 백엔드: `@Scheduled` 매분 실행, `last_notified_on` 선점으로 중복 발송 방지, Expo Push 호출과 `DeviceNotRegistered` 정리
- 앱: 푸시 토큰 등록, 알림 카테고리(액션 버튼), 알림에서 열린 앱의 자동 기록
- 2단계가 끝난 뒤 도그푸딩과 병행해서 진행해도 된다.

### 4. 보강

- 스트릭·준수율 계산(윈도 함수), 통계 화면
- 소급 기록·정정 UI(`record/[date]`): 과거 날짜는 제한 없이 허용([API 명세 D3](API_SPEC.md))
- 색에 의존하지 않는 상태 표시, 다크 모드 3색 구분 확인

### 5. 배포·도그푸딩

- NCP 서버, Docker Compose, nginx TLS, 도메인
- **운영 준비:** 로그 확인 방법, 에러 추적 수단, `pg_dump` 백업과 **복구 훈련**(백업은 복구해 봐야 믿을 수 있다)
- CI에 배포(CD) 추가
- **개인정보처리방침·App Privacy 정보:** TestFlight 외부 배포와 App Store 심사에 필요하다. 수집 항목은 소셜 계정 식별자, 타임존, 식습관 기록, 푸시 토큰이다.
- TestFlight 배포 후 30일 연속 기록으로 1차 성공 기준 검증
- 결정 필요: TestFlight만 쓸지, App Store에 낼지(PRD의 "공개 서비스로 운영 가능한 구조"와 연결)

## 순서에 대한 판단

- **인증을 핵심 루프보다 먼저 둔다.** 모든 API가 사용자 식별을 전제로 하므로, 고정 사용자로 먼저 만들면 나중에 전 구간을 고쳐야 한다.
- **설계를 구현보다 먼저 둔다.** 이 프로젝트는 백엔드 OpenAPI 스펙에서 앱 타입을 생성하므로([기술 스택](TECH_STACK.md)), API 계약이 흔들리면 백엔드와 앱이 함께 흔들린다.
- **알림은 핵심 루프 뒤에 둔다.** 외부 의존(실기기, APNs)이 크고, 핵심 루프가 없으면 알림이 가리킬 곳이 없다.
